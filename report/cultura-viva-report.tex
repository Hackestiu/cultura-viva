\begin{abstract}
\noindent
Cultura Viva is an interactive multimodal AI audio guide for Antoni Gaud\'i's
monuments in Barcelona --- Sagrada Fam\'ilia, Park G\"uell, Casa Mil\`a
(La Pedrera) and Casa Batll\'o --- running \emph{entirely on-device} on an
Arduino UNO Q. A visitor photographs an architectural element, asks a question
aloud, and hears a spoken answer in the guide personality they picked. No
network round-trip is involved at inference time.

This report documents the engineering work behind the device: the four-stage
pipeline (vision $\rightarrow$ speech-to-text $\rightarrow$ knowledge retrieval
$+$ small language model $\rightarrow$ speech synthesis), the comparative
benchmarks that selected each model under the board's memory and latency
budget, the latency optimisations that make the interaction feel immediate, and
the bill of materials with per-component prices.
\end{abstract}

\section{System overview}

\subsection{Target platform}

The whole system runs on a single Arduino UNO Q, which is a dual-brain board:

\begin{itemize}
  \item \textbf{STM32 microcontroller (MCU).} Real-time C++ Arduino sketch
        driving the ST7735S LCD, the physical inputs (mode switch, action
        button, Modulino buttons/knob), the Modulino buzzer, GPS ingestion and
        minimap rendering.
  \item \textbf{Qualcomm QRB2210 Linux processor (MPU).} Quad-core ARM
        Cortex-A53 @ \SI{2.0}{\giga\hertz}, LPDDR4 RAM, \SI{32}{\giga\byte}
        eMMC, Debian Linux. Runs the Python AI pipeline: ONNX vision
        classification, faster-whisper STT, knowledge-graph retrieval, a
        quantised small language model via
        \texttt{llama-cpp-\discretionary{}{}{}python}, and Piper TTS.
\end{itemize}

The two halves talk over Arduino Bridge RPC. The board variant used for all
measurements reports \SI{3667}{\mega\byte} of usable RAM, i.e.\ the 4\,GB
model.

\subsection{The pipeline}

\Cref{fig:pipeline} shows the full interaction. Two things about its
shape are worth stating up front, because they are easy to get wrong from a
prose description.

\begin{itemize}
  \item \textbf{The guide personality is chosen before any photo is taken.}
        It is a setup step, not a step in the answering loop: the visitor picks
        Artistic, Technical or Child on the Modulino buttons, and that choice
        then governs both the system prompt handed to the SLM and the Piper
        voice used for playback. Because the personality is already fixed when
        a photo is confirmed, the whole stable prompt prefix --- personality
        instructions plus the recognised element's fact sheet --- is known
        before the visitor has said a word, which is exactly what makes the
        prefill overlap in \Cref{sec:latency} possible.
  \item \textbf{The GPS does one job only: it picks which minimap is shown.}
        The NEO-6M feeds a coordinate to a Haversine site resolver that decides
        whether the visitor is at Park G\"uell, the Sagrada Fam\'ilia, Casa
        Mil\`a or Casa Batll\'o, and the LCD switches to that monument's
        tilemap and landmark set. It takes no part in recognition and no part
        in the answer: the element is identified from the photograph alone, and
        the knowledge lookup is keyed on the classifier's element ID. With no
        GPS fix the guide still works end to end --- only the map defaults to
        the configured location instead of following the visitor.
\end{itemize}

\noindent The nine steps in detail:

\begin{enumerate}
  \item \textbf{Choose a personality.} Artistic, Technical or Child, on the
        Modulino buttons. Sets the SLM system prompt and the TTS voice.
  \item \textbf{Frame.} In camera mode (switch D6 high), the live view is
        streamed to the LCD as Base64 RGB565 chunks over Bridge RPC.
  \item \textbf{Capture.} Button D7 takes a 1080p photo.
  \item \textbf{Validate.} The per-monument ONNX classifier decides
        \emph{which architectural element} is in frame, or rejects the photo as
        off-distribution and asks for a retake (\Cref{sec:ood}).
  \item \textbf{Ask.} The visitor flips to map mode and records a spoken
        question. Recording ends by itself on silence.
  \item \textbf{Transcribe.} faster-whisper, biased towards the domain
        vocabulary (``Gaud\'i'', ``trencad\'is'', ``Sagrada Fam\'ilia'',
        \ldots) through an \texttt{initial\_prompt}.
  \item \textbf{Ground.} The recognised element ID indexes directly into a
        curated knowledge base (\texttt{knowledge\_base.json},
        \texttt{element\_sheets.json}), with keyword search as fallback.
  \item \textbf{Answer.} The retrieved facts, the personality prompt and the
        question go to the SLM, which decodes sentence by sentence.
  \item \textbf{Speak.} Piper synthesises each sentence and streams it to ALSA
        while the SLM decodes the next. Volume tracks the Modulino knob live,
        and the visited landmark is marked on the minimap.
\end{enumerate}

\subsection{Design constraints}

Every model choice in this report was made against the same budget:

\begin{center}
\begin{tabular}{lp{9.2cm}}
\toprule
\textbf{Constraint} & \textbf{Value} \\
\midrule
Compute            & 4$\times$ ARM Cortex-A53 @ \SI{2.0}{\giga\hertz}, CPU only \\
RAM for SLM weights + context & $<\SI{1.5}{\giga\byte}$ \\
SLM context window & 2048 tokens \\
Target response latency & $<\SI{3}{\second}$ to first audio \\
Connectivity at inference time & none (fully offline) \\
\bottomrule
\end{tabular}
\end{center}

There is no GPU backend: the \texttt{llama.cpp} build on the board is CPU-only,
and ONNX Runtime uses the CPU execution provider.

\subsection{Problem formulation}

The vision stage answers ``\emph{what} is the visitor pointing at?''. It is a
per-monument classification problem, not a single global one: each monument has
its own set of architectural elements, so the label spaces are disjoint and a
shared classification head would be meaningless. We therefore train one
classifier per $(\text{monument}, \text{model})$ pair.

Split seed & 42 \\

Normalisation & mean $0.5$, std $0.5$ per channel \\
\bottomrule

Training and calibration both go through the same dataset loader, which

\paragraph{Deployed Models.} The device ships with four location-specific ONNX classifiers (one per monument), plus an \texttt{unknown} label. Each model directory pairs the \texttt{model.onnx} file with a \texttt{labels.json} containing necessary metadata (label map, input size, and normalisation constants). This decoupled design allows the board-side code to switch monuments seamlessly with a simple directory change, requiring no code recompilation.

\subsection{Out-of-distribution rejection}
\label{sec:ood}

To prevent the system from confidently hallucinating answers for irrelevant photos (e.g., trees, skies, or passers-by), the pipeline must reject invalid inputs as \texttt{not\_sure}. 

\paragraph{Deployed implementation.} While the repository contains a script (\texttt{calibrate\_thresholds.py}) to compute dynamic, per-checkpoint thresholds based on predictive entropy, this is not used on the device. Instead, the board relies entirely on a simple, fixed peak confidence threshold across all monuments:

\begin{equation}
\max_i p_i \;<\; 0.50
\end{equation}

If the highest predicted probability is below 50\,\%, the input is rejected. This flat cut proved perfectly sufficient in practice, as completely out-of-distribution photos consistently yield dispersed probabilities well below this mark, making complex calibration unnecessary for robust rejection.

\subsection{Export path}

\begin{enumerate}
  \item \texttt{train\_classifier.py} --- fine-tunes every
        $(\text{monument}, \text{model})$ combination in \texttt{config.yaml}.
  \item \texttt{export\_to\_onnx.py} --- converts one fine-tuned checkpoint
        into \texttt{model.onnx} $+$ \texttt{labels.json}.
  \item \texttt{calibrate\_thresholds.py} --- suggests per-checkpoint OOD
        thresholds. Available, but not used by the shipped configuration
        (\Cref{sec:ood}).
  \item \texttt{inference.py} --- runs an exported checkpoint on a single image
        with the gate applied; also importable as \texttt{MonumentClassifier},
        which is how the device uses it.
\end{enumerate}

\subsubsection{Protocol}

\begin{itemize}
  \item \textbf{Test set.} 38 curated Gaud\'i questions with reference answers
        and retrieved contexts (\texttt{eval/testset.json}).
  \item \textbf{Generation.} \texttt{temperature} $=0.1$,
        \texttt{max\_tokens} $=60$, \texttt{repeat\_penalty} $=1.1$,
        stop sequences \texttt{"\textbackslash n\textbackslash n"} and
        \texttt{<|im\_end|>}, context window 2048, 4 threads, batch size 256.
        These deliberately mirror what the device passes to
        \texttt{create\_chat\_completion}: a benchmark run with a different
        token budget or stop condition stops describing what actually ships.
  \item \textbf{Retrieval.} Top-3 passages from the knowledge base, scored
        semantically. This differs from the device, which looks an element up
        directly by the ID the vision stage gives it --- the test set carries no
        element IDs and includes architect-level and cross-monument questions,
        so semantic retrieval is the only option here.
  \item \textbf{Personalities.} Each candidate is run under all three guide
        voices (Artistic, Technical, Child), producing a separate predictions
        file per personality.
  \item \textbf{Judge.} Ragas, scoring \emph{Faithfulness},
        \emph{AnswerRelevancy}, \emph{ContextPrecision} and
        \emph{ContextRecall}, driven by a \emph{local} Ollama judge
        (\texttt{qwen2.5:7b}, temperature $0$) with
        \texttt{all-MiniLM-L6-v2} sentence embeddings. Keeping the judge local
        means the evaluation is reproducible offline and no test data leaves
        the machine.
  \item \textbf{On-device re-run.} \texttt{benchmark\_arduino.py} re-runs the
        same 38 questions on the Cortex-A53 through
        \texttt{llama-cpp-python} built with
        \texttt{-march=armv8-a -mtune=cortex-a53}, and the resulting
        predictions are scored with the same Ragas judge back on the PC.
\end{itemize}

\subsubsection{Guide personalities}
\label{sec:slm-personalities}

The guide personality is the one setting a visitor chooses for themselves, so it
is worth asking whether it changes anything. It is implemented as a system-prompt
tail: the retrieved facts are identical for all three guides by construction
(\texttt{get\_kg\_context} is personality-independent), and only a short block of
instructions differs.

\paragraph{Protocol.} 24 open questions, one per element sheet
(\texttt{personality/probes.json}) --- open rather than factual because a closed
question collapses to one correct sentence whatever the guide. Each carries an
\texttt{element\_id}, so retrieval takes the direct-lookup path the device uses
when vision names an element. Every question is answered by all three guides on
\texttt{qwen2.5:0.5b} at the shipped sampling settings, giving 72 answers. A judge
from a \emph{different} model family, \texttt{llama3.1:8b}, then reads each answer
blind and names the guide that wrote it, choosing from paraphrased descriptions
rather than the prompt text, with the options shuffled per item.

\paragraph{The guides are not distinguishable.}

\begin{table}[h]
\centering
\caption{Blind identification of the guide from its answer. Rows are the guide
that wrote the answer, columns the judge's choice; the diagonal is correct.}
\begin{tabular}{lrrr}
\toprule
\textbf{true \textbackslash\ predicted} & \textbf{artistic} & \textbf{technical} & \textbf{child} \\
\midrule
artistic  & \textbf{14} & 10 & 0 \\
technical & 8  & \textbf{13} & 3 \\
child     & 12 & 11 & \textbf{1} \\
\bottomrule
\end{tabular}
\end{table}

28 of 72 correct, \SI{38.9}{\percent}, against a \SI{33.3}{\percent} chance
baseline --- an exact binomial $p = 0.19$, indistinguishable from guessing. The
matrix shows where it breaks down: the judge chose \emph{child} four times in 72,
so the child guide is recovered in \SI{4}{\percent} of its own answers. Reading
the output agrees with the number. Asked why Casa Batll\'o's facade resembles
bones, the child guide replies that it ``gives it a sense of solidity and
strength'', which is not a sentence written for an eight-year-old.

\paragraph{This is not an artefact of the judge.} Given three hand-written,
deliberately distinct texts, the same judge scores 3/3 and picks \emph{child}
correctly --- the label it almost never chose on real output. The instrument
discriminates; the guides simply sound alike. This self-test runs on every
invocation so the null always ships with evidence the measurement works.

\paragraph{What it cannot say.} Without a positive control arm --- a deliberately
loud persona run under the same constraints --- this result cannot separate two
causes with opposite remedies: that the three prompts are too similar to each
other, or that the regime suppresses any persona at all. Both are plausible. Each
prompt is roughly 58 words of which about 28 are verbatim-identical across all
three, so only some 30 words distinguish a guide; and one of the shared sentences
(``answer ONLY what the user asks --- do not give unsolicited background'')
forbids precisely the elaboration in which register lives, under a 50-word
instruction and a 60-token cap that truncated \SIrange{29}{38}{\percent} of
answers mid-sentence.

\paragraph{A larger finding: grounding.} The same judge was asked, for each
answer, whether every claim was supported by the facts the model had been given
--- reference-free, so that style is not scored as inaccuracy.

Between a half and two thirds of answers contain something the sheets do not
support. Spot-checks confirm the judge is not being harsh: the model states that

sheet describes a covered market. On the evidence here this matters considerably
more than which of the three voices delivers it, and it is the open item this
benchmark would pursue next.

\paragraph{Recommendation.} Small models follow format constraints far more
reliably than tone instructions. Replacing ``you speak with passion and use
evocative metaphors'' with a concrete output requirement per guide --- name one
visual image; cite one number when the facts provide one; include one everyday
comparison --- is the cheapest change likely to move this result, and it can be
re-measured with \texttt{uv run python main.py personality}.

\paragraph{Selected.} \textbf{Qwen 2.5 0.5B Instruct}, \texttt{Q4\_K\_M}
(\texttt{qwen2.5-0.5b-instruct-q4\_k\_m.gguf}).

Given that generation latency did not separate the candidates, the decision
came down to what the model costs the rest of the system. At
\SI{0.65}{\giga\byte} for weights plus a 2k context, the 0.5B model is less
than half the working set of the 1.5B one (\SI{1.45}{\giga\byte}) and under
half of SmolLM2 (\SI{1.50}{\giga\byte}). That difference is not academic: the
SLM is not alone on the board. The vision classifier, faster-whisper
(\SI{397}{\mega\byte} peak, \S\ref{sec:stt}), Piper and the persisted prefix
caches all have to be resident at the same time, on a device that is also
driving a camera, a display and audio. Choosing the smallest candidate that
answers the questions acceptably is what keeps the pipeline from contending for
memory mid-interaction --- and it shortens the cold prefill that
\texttt{prewarm\_cache.py} has to precompute for all 24 elements.

The answer quality that ``acceptably'' refers to is the Ragas comparison above,
which still has to be regenerated and filled in.

\subsection{Speech-to-text}
\label{sec:stt}
% ---------------------------------------------------------------------------

\subsubsection{Engine Evaluation}

To find the optimal trade-off between keyword retention, memory footprint, and inference latency on the Cortex-A53, several speech-to-text architectures were benchmarked: \texttt{faster-whisper} (CTranslate2), \texttt{whisper.cpp} (GGML), \texttt{sherpa-onnx}, and \texttt{vosk}. For the Whisper-based engines, both \texttt{tiny.en} and \texttt{base.en} tiers were evaluated. The English-only (\texttt{.en}) variants were deliberately chosen since the guide answers in English, and monolingual weights are both smaller and more accurate than their multilingual counterparts at the same parameter count.

\subsubsection{Metrics and domain biasing}

The harness measures Word Error Rate (WER), Character Error Rate (CER), Keyword-spotting Accuracy (KWA), Real-Time Factor (RTF), and peak RAM.

Keyword-spotting accuracy deserves a special note. It is measured against a curated list of domain aliases (e.g., ``La Pedrera'' or ``catenary arch''). A generic WER number hides the failure that actually matters for an audio guide: a transcript that gets ``Gaud\'i'' or ``trencad\'is'' wrong will retrieve the wrong knowledge sheet, and the whole answer is then confidently off-topic. 

To prevent this, the decoder is biased towards the domain vocabulary by injecting the following literal string as the \texttt{initial\_prompt}:

\begin{quote}\ttfamily\small
"Cultura Viva audio guide in Barcelona about Antoni Gaud\'i, Sagrada Fam\'ilia basilica, 
Nativity, Passion, and Glory facades, Catalan modernisme architecture, Casa Batll\'o, 
Casa Mil\`a, Park G\"uell, dragon and salamander sculptures, and trencad\'is mosaics."
\end{quote}

\subsubsection{Results and selection}

The evaluation set consisted of \textbf{24 synthetic visitor utterances}, varied across register (neutral, polite, child-like), intent (materials, history), and speaker voice, with controlled background noise.

The benchmark clearly highlights the architectural trade-offs. While \texttt{sherpa-onnx} is exceptionally fast (RTF 0.07), its keyword accuracy (50\,\%) makes it unusable for a domain-specific guide. Stepping down to a \texttt{tiny.en} model degrades keyword spotting unacceptably to 79\,\%. The \texttt{base.en} tier is the smallest Whisper model that holds up on full sentences. 

\paragraph{What ships.} \textbf{\texttt{faster-whisper}} with the \texttt{base.en} model at INT8 (\texttt{models/stt/faster-whisper-base.en}). A \SI{16.4}{\percent} word error rate alongside a \SI{96.1}{\percent} keyword accuracy is exactly the shape we were optimising for: the transcript is imperfect in its function words but almost never wrong about the proper nouns that drive retrieval. 

To maximise performance on the board, the shipped engine is configured with:
\begin{itemize}
  \item \textbf{Explicit hotwords} --- passing the domain aliases directly to the CTranslate2 decoder.
  \item \textbf{4 CPU threads} --- the QRB2210 has exactly 4 Cortex-A53 cores; matching this saturates the CPU without context-switch overhead.
  \item \textbf{INT8 compute type} --- keeps the model well inside the LPDDR4 memory and maximises memory bandwidth, which is the binding constraint here.
  \item \textbf{Greedy decoding} --- \texttt{temperature} $=0.0$ and \texttt{beam\_size} $=1$ to minimise RTF.
\end{itemize}

\subsubsection{Candidates}

18 ONNX voices are registered in \texttt{models\_config.json}: three VITS
models exported from Hugging Face (MMS-TTS English, VITS LJSpeech, VITS VCTK)
and 15 Piper voices --- Lessac, Ryan, Amy, Alan and Cori, each in low, medium

\textbf{The field narrowed to Piper, on the inference-time / quality
trade-off.} The VITS exports were included as the obvious general-purpose
baseline and were eliminated by the numbers below: at RTF $\approx 3.8$ they
are far too slow for a device that has to answer while the visitor is standing
in front of the building, and the naturalness they return for that cost is not
better than a Piper medium voice. Piper, built for exactly this class of
hardware, reaches acceptable voice quality at RTF well under 1 --- and,
crucially, is tiered, so quality can be traded against compute by swapping a
voice file rather than changing the runtime. That tiering is what the rest of
this section measures.

Audio quality is not scored here --- the benchmark measures \emph{inference
time and footprint only}. Which specific Piper voice suits which guide
personality was decided separately, by ear.

\subsubsection{Reading the results}

Table~\ref{tab:tts} separates the field cleanly into three groups.

\begin{itemize}
  \item \textbf{The VITS exports are unusable here.} RTF $\approx 3.8$ means
        roughly four seconds of compute per second of speech. A 20-second
        answer would take over a minute to synthesise.
  \item \textbf{Piper ``high'' voices are equally unusable}, and for the same
        reason --- RTF $\approx 5.2$--$5.3$, \emph{worse} than the VITS models
        despite Piper's much lighter runtime. The quality tier, not the
        framework, is what blows the budget.
  \item \textbf{Piper low and medium clear the bar with room to spare.} Every
        low voice lands at RTF $\approx 0.61$--$0.64$ and every medium voice at
        $\approx 0.75$--$0.81$. A medium voice synthesises a short sentence in
        about \SI{2}{\second} and a long one in about \SI{8}{\second}, while
        producing more audio than that in playback time --- which is what makes
        sentence-level streaming \Cref{sec:latency} work: playback of
        sentence $N$ outlasts synthesis of sentence $N+1$, so the audio never
        stalls.
\end{itemize}

The gap between low and medium is around \SI{25}{\percent} of compute for a
clearly better voice, which is worth paying given the headroom.

\subsection{End-to-end latency}
\label{sec:latency}

Adding up every pipeline stage measured in isolation gives an unrealistic upper bound, as the device does not run them strictly sequentially. To evaluate real-world user experience, the benchmark reports \textbf{Time to First Audio (TTFA)}: the delay from the moment the visitor stops speaking to the first generated word. 

Three mechanisms heavily optimise this perceived latency by overlapping operations:

\begin{itemize}
  \item \textbf{Asynchronous prefill.} The static prompt prefix (personality and knowledge facts) is prefilled into the KV-cache on a background thread while the visitor is still speaking, leaving only the question to be processed at the end.
  \item \textbf{Silence cropping.} Recording automatically trims silent margins before passing the audio to Whisper, preventing the encoder from wasting compute on padded room tone.
  \item \textbf{Sentence-level streaming.} Rather than waiting for the full SLM output, tokens are emitted per sentence. Piper synthesises sentence $N$ while the SLM decodes sentence $N+1$, ensuring audio playback never stalls.
\end{itemize}

Together, these concurrent techniques transform the TTFA from a naive sequential sum of all stages into a highly optimised pipeline:

\begin{equation*}
\text{TTFA} \approx \text{STT} + \text{warm prefill} + \text{decode}_{n=1} + \text{TTS}_{n=1}
\end{equation*}

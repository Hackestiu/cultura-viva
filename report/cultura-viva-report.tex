\begin{abstract}
\noindent
Cultura Viva is an interactive multimodal AI audio guide for Antoni Gaud\'i's
monuments in Barcelona --- Sagrada Fam\'ilia, Park G\"uell, Casa Mil\`a
(La Pedrera) and Casa Batll\'o --- running \emph{entirely on-device} on an
Arduino UNO Q. A visitor photographs an architectural element, asks a question
aloud, and hears a spoken answer in the guide personality they picked. No
network round-trip is involved at inference time.

This report documents the engineering work behind the device: the four-stage
pipeline (vision $\rightarrow$ speech-to-text $\rightarrow$ knowledge retrieval
$+$ small language model $\rightarrow$ speech synthesis), the comparative
benchmarks that selected each model under the board's memory and latency
budget, the latency optimisations that make the interaction feel immediate, and
the bill of materials with per-component prices.
\end{abstract}

\section{System overview}

\subsection{Target platform}

The whole system runs on a single Arduino UNO Q, which is a dual-brain board:

\begin{itemize}
  \item \textbf{STM32 microcontroller (MCU).} Real-time C++ Arduino sketch
        driving the ST7735S LCD, the physical inputs (mode switch, action
        button, Modulino buttons/knob), the Modulino buzzer, GPS ingestion and
        minimap rendering.
  \item \textbf{Qualcomm QRB2210 Linux processor (MPU).} Quad-core ARM
        Cortex-A53 @ \SI{2.0}{\giga\hertz}, LPDDR4 RAM, \SI{32}{\giga\byte}
        eMMC, Debian Linux. Runs the Python AI pipeline: ONNX vision
        classification, faster-whisper STT, knowledge-graph retrieval, a
        quantised small language model via
        \texttt{llama-cpp-\discretionary{}{}{}python}, and Piper TTS.
\end{itemize}

The two halves talk over Arduino Bridge RPC. The board variant used for all
measurements reports \SI{3667}{\mega\byte} of usable RAM, i.e.\ the 4\,GB
model.

\subsection{The pipeline}

Figure~\ref{fig:pipeline} shows the full interaction. Two things about its
shape are worth stating up front, because they are easy to get wrong from a
prose description.

\begin{itemize}
  \item \textbf{The guide personality is chosen before any photo is taken.}
        It is a setup step, not a step in the answering loop: the visitor picks
        Artistic, Technical or Child on the Modulino buttons, and that choice
        then governs both the system prompt handed to the SLM and the Piper
        voice used for playback. Because the personality is already fixed when
        a photo is confirmed, the whole stable prompt prefix --- personality
        instructions plus the recognised element's fact sheet --- is known
        before the visitor has said a word, which is exactly what makes the
        prefill overlap in \S\ref{sec:latency} possible.
  \item \textbf{The GPS does one job only: it picks which minimap is shown.}
        The NEO-6M feeds a coordinate to a Haversine site resolver that decides
        whether the visitor is at Park G\"uell, the Sagrada Fam\'ilia, Casa
        Mil\`a or Casa Batll\'o, and the LCD switches to that monument's
        tilemap and landmark set. It takes no part in recognition and no part
        in the answer: the element is identified from the photograph alone, and
        the knowledge lookup is keyed on the classifier's element ID. With no
        GPS fix the guide still works end to end --- only the map defaults to
        the configured location instead of following the visitor.
\end{itemize}

\noindent The nine steps in detail:

\begin{enumerate}
  \item \textbf{Choose a personality.} Artistic, Technical or Child, on the
        Modulino buttons. Sets the SLM system prompt and the TTS voice.
  \item \textbf{Frame.} In camera mode (switch D6 high), the live view is
        streamed to the LCD as Base64 RGB565 chunks over Bridge RPC.
  \item \textbf{Capture.} Button D7 takes a 1080p photo.
  \item \textbf{Validate.} The per-monument ONNX classifier decides
        \emph{which architectural element} is in frame, or rejects the photo as
        off-distribution and asks for a retake (\S\ref{sec:ood}).
  \item \textbf{Ask.} The visitor flips to map mode and records a spoken
        question. Recording ends by itself on silence.
  \item \textbf{Transcribe.} faster-whisper, biased towards the domain
        vocabulary (``Gaud\'i'', ``trencad\'is'', ``Sagrada Fam\'ilia'',
        \ldots) through an \texttt{initial\_prompt}.
  \item \textbf{Ground.} The recognised element ID indexes directly into a
        curated knowledge base (\texttt{knowledge\_base.json},
        \texttt{element\_sheets.json}), with keyword search as fallback.
  \item \textbf{Answer.} The retrieved facts, the personality prompt and the
        question go to the SLM, which decodes sentence by sentence.
  \item \textbf{Speak.} Piper synthesises each sentence and streams it to ALSA
        while the SLM decodes the next. Volume tracks the Modulino knob live,
        and the visited landmark is marked on the minimap.
\end{enumerate}

\subsection{Design constraints}

Every model choice in this report was made against the same budget:

\begin{center}
\begin{tabular}{lp{9.2cm}}
\toprule
\textbf{Constraint} & \textbf{Value} \\
\midrule
Compute            & 4$\times$ ARM Cortex-A53 @ \SI{2.0}{\giga\hertz}, CPU only \\
RAM for SLM weights + context & $<\SI{1.5}{\giga\byte}$ \\
SLM context window & 2048 tokens \\
Target response latency & $<\SI{3}{\second}$ to first audio \\
Connectivity at inference time & none (fully offline) \\
\bottomrule
\end{tabular}
\end{center}

There is no GPU backend: the \texttt{llama.cpp} build on the board is CPU-only,
and ONNX Runtime uses the CPU execution provider.

\subsection{Problem formulation}

The vision stage answers ``\emph{what} is the visitor pointing at?''. It is a
per-monument classification problem, not a single global one: each monument has
its own set of architectural elements, so the label spaces are disjoint and a
shared classification head would be meaningless. We therefore train one
classifier per $(\text{monument}, \text{model})$ pair.

\subsection{Out-of-distribution rejection}
\label{sec:ood}

A real visitor will point the camera at a tree, another tourist, or the sky. A
plain \texttt{argmax} classifier is obliged to name an architectural element
anyway, which would produce a confident, grounded, entirely wrong audio guide
answer. The pipeline therefore puts a gate in front of the prediction. The
input is rejected as \texttt{not\_sure} when \emph{either} signal fires:

\begin{align}
H(p) = -\sum_{i=1}^{N} p_i \ln p_i \;&>\; \tau_{H}
  &&\text{(predictive entropy too high)}\\[0.2em]
\max_i p_i \;&<\; \tau_{\text{conf}}
  &&\text{(peak confidence too low)}
\end{align}

with $\tau_{H} = 0.5 \ln N$, auto-scaled to each monument's class count so that
a 2-class and a 7-class head are held to comparable standards.

\paragraph{What actually runs on the board.} A fixed
$\tau_{\text{conf}} = 0.50$, the same value for all four monuments and both
backbones. Per-checkpoint calibration was deliberately not deployed.

\texttt{calibrate\_thresholds.py} exists and does the fuller job --- it sweeps
the validation split and suggests a $(\tau_{H}, \tau_{\text{conf}})$ pair for a
given checkpoint subject to a recall target (default: preserve 95\,\% of
in-distribution recall), printing a ready-to-paste YAML snippet, and
\texttt{inference.py} will merge overrides across three levels
(\emph{global $\rightarrow$ monument $\rightarrow$ model}, most specific
winning). None of that is in use on the device. A flat 50\,\% confidence cut
proved good enough in practice: the failure it has to catch is a photo of
foliage or a passer-by, which lands nowhere near 50\,\% confidence on any of
the heads, so the extra precision bought by per-checkpoint tuning would not
have changed which photos get rejected. Calibration remains available if a
future monument turns out to need it.

\subsection{Export path}

\begin{enumerate}
  \item \texttt{train\_classifier.py} --- fine-tunes every
        $(\text{monument}, \text{model})$ combination in \texttt{config.yaml}.
  \item \texttt{export\_to\_onnx.py} --- converts one fine-tuned checkpoint
        into \texttt{model.onnx} $+$ \texttt{labels.json}.
  \item \texttt{calibrate\_thresholds.py} --- suggests per-checkpoint OOD
        thresholds. Available, but not used by the shipped configuration
        (\S\ref{sec:ood}).
  \item \texttt{inference.py} --- runs an exported checkpoint on a single image
        with the gate applied; also importable as \texttt{MonumentClassifier},
        which is how the device uses it.
\end{enumerate}

\subsubsection{Protocol}

\begin{itemize}
  \item \textbf{Test set.} 38 curated Gaud\'i questions with reference answers
        and retrieved contexts (\texttt{eval/testset.json}).
  \item \textbf{Generation.} \texttt{temperature} $=0.1$,
        \texttt{max\_tokens} $=60$, \texttt{repeat\_penalty} $=1.1$,
        stop sequences \texttt{"\textbackslash n\textbackslash n"} and
        \texttt{<|im\_end|>}, context window 2048, 4 threads, batch size 256.
        These deliberately mirror what the device passes to
        \texttt{create\_chat\_completion}: a benchmark run with a different
        token budget or stop condition stops describing what actually ships.
  \item \textbf{Retrieval.} Top-3 passages from the knowledge base, scored
        semantically. This differs from the device, which looks an element up
        directly by the ID the vision stage gives it --- the test set carries no
        element IDs and includes architect-level and cross-monument questions,
        so semantic retrieval is the only option here.
  \item \textbf{Personalities.} Each candidate is run under all three guide
        voices (Artistic, Technical, Child), producing a separate predictions
        file per personality.
  \item \textbf{Judge.} Ragas, scoring \emph{Faithfulness},
        \emph{AnswerRelevancy}, \emph{ContextPrecision} and
        \emph{ContextRecall}, driven by a \emph{local} Ollama judge
        (\texttt{qwen2.5:7b}, temperature $0$) with
        \texttt{all-MiniLM-L6-v2} sentence embeddings. Keeping the judge local
        means the evaluation is reproducible offline and no test data leaves
        the machine.
  \item \textbf{On-device re-run.} \texttt{benchmark\_arduino.py} re-runs the
        same 38 questions on the Cortex-A53 through
        \texttt{llama-cpp-python} built with
        \texttt{-march=armv8-a -mtune=cortex-a53}, and the resulting
        predictions are scored with the same Ragas judge back on the PC.
\end{itemize}

\subsubsection{Guide personalities}
\label{sec:slm-personalities}

The guide personality is the one setting a visitor chooses for themselves, so it
is worth asking whether it changes anything. It is implemented purely as a
system-prompt tail: \texttt{get\_kg\_context} is personality-independent, so all
three guides receive byte-identical facts and differ only in a short block of
instructions.

\paragraph{Protocol.} 24 open questions, one per element sheet, each carrying an
\texttt{element\_id} so retrieval takes the direct-lookup path the device uses
when vision names an element. Every question is answered by all three guides at
the shipped sampling settings. A judge from a \emph{different} model family,
\texttt{llama3.1:8b}, then reads each answer blind and names the guide that wrote
it, choosing between paraphrased descriptions rather than the prompt text, with
the options shuffled per item. Chance is therefore \SI{33.3}{\percent}. The same
judge is given three hand-written, deliberately distinct texts as a self-test on
every run; it scored 3/3 throughout, so a null result is a statement about the
guides and not about the instrument.

\paragraph{Tone instructions did not work.} The original prompts described how
each guide should sound --- ``you speak with passion and use evocative
metaphors'', ``you are precise, rigorous'', ``you use simple analogies and an
animated tone''. On \texttt{qwen2.5:0.5b} the judge recovered the intended guide
in \textbf{28 of 72} answers, \SI{38.9}{\percent} against a \SI{33.3}{\percent}
baseline (exact binomial $p = 0.19$): indistinguishable from guessing. The child
guide was identified in \SI{4}{\percent} of its own answers. Asked why Casa
Batll\'o's facade resembles bones, it replied that this ``gives it a sense of
solidity and strength''.

\paragraph{Format requirements replaced them.} Each guide now demands one
concrete, mechanically checkable thing, and the three are deliberately orthogonal
so that a guide which obeys is distinguishable from one which does not:

\begin{itemize}
  \item \textbf{artistic} --- one comparison to nature, written as ``like \ldots'';
  \item \textbf{technical} --- at least one number written in digits, taken from
        the facts supplied;
  \item \textbf{child} --- a closing question, ending in a question mark.
\end{itemize}

\subsection{Speech-to-text}
\label{sec:stt}
% ---------------------------------------------------------------------------

\subsubsection{Engine}

One engine was benchmarked and shipped: \textbf{faster-whisper} on the Whisper
\texttt{base.en} model, running under CTranslate2 with INT8 quantisation.

\texttt{base.en} is the smallest Whisper tier that holds up on full sentences,
and CTranslate2's INT8 path is what makes it viable on four Cortex-A53 cores:
it keeps the \SI{141}{\mega\byte} model and its activations well inside LPDDR4
and maximises memory bandwidth, which is the binding constraint here rather
than arithmetic. The English-only (\texttt{.en}) variant is deliberate --- the
guide answers in English, and the monolingual weights are both smaller and more
accurate on English than the multilingual ones at the same size.

\subsubsection{Metrics and optimisations}

The harness measures \textbf{WER}, \textbf{CER}, \textbf{keyword-spotting
accuracy}, \textbf{real-time factor} (inference time / audio duration) and
\textbf{peak RAM}.

Keyword-spotting accuracy deserves a note. A generic WER number hides the
failure that actually matters for an audio guide: a transcript that gets
``Gaud\'i'', ``trencad\'is'' or ``Sagrada Fam\'ilia'' wrong will retrieve the
wrong knowledge sheet, and the whole answer is then confidently off-topic. The
decoder is therefore biased towards the domain vocabulary through an
\texttt{initial\_prompt}:

\begin{quote}\itshape\small
Cultura Viva audio guide in Barcelona about Antoni Gaud\'i, Sagrada Fam\'ilia
basilica, Nativity, Passion, and Glory facades, Catalan modernisme
architecture, Casa Batll\'o, Casa Mil\`a, Park G\"uell, dragon and salamander
sculptures, and trencad\'is mosaics.
\end{quote}

For \texttt{faster-whisper} the same terms are additionally passed as explicit
\texttt{hotwords}. Further tuning:

\begin{itemize}
  \item \textbf{4 CPU threads} --- the QRB2210 has exactly 4 Cortex-A53 cores,
        so 4 saturates the CPU without paying context-switch overhead.
  \item \textbf{INT8 compute type} --- keeps the model comfortably inside
        LPDDR4 and maximises memory bandwidth.
  \item \textbf{Greedy decoding} --- \texttt{temperature} $=0.0$,
        \texttt{beam\_size} $=1$, to minimise RTF.
\end{itemize}

\subsubsection{Results}

The evaluation set is \textbf{24 synthetic visitor utterances}, varied across
register (neutral, polite, child-like), intent (materials, history, \ldots) and
speaker voice, with controlled background noise, each annotated with its target
keywords.

\subsubsection{Candidates}

18 ONNX voices are registered in \texttt{models\_config.json}: three VITS
models exported from Hugging Face (MMS-TTS English, VITS LJSpeech, VITS VCTK)
and 15 Piper voices --- Lessac, Ryan, Amy, Alan and Cori, each in low, medium
and high quality. 15 of the 18 were actually timed;
\texttt{piper-amy-high}, \texttt{piper-alan-high} and \texttt{piper-cori-low}

\textbf{The field narrowed to Piper, on the inference-time / quality
trade-off.} The VITS exports were included as the obvious general-purpose
baseline and were eliminated by the numbers below: at RTF $\approx 3.8$ they
are far too slow for a device that has to answer while the visitor is standing
in front of the building, and the naturalness they return for that cost is not
better than a Piper medium voice. Piper, built for exactly this class of
hardware, reaches acceptable voice quality at RTF well under 1 --- and,
crucially, is tiered, so quality can be traded against compute by swapping a
voice file rather than changing the runtime. That tiering is what the rest of
this section measures.

Audio quality is not scored here --- the benchmark measures \emph{inference
time and footprint only}. Which specific Piper voice suits which guide
personality was decided separately, by ear.

\subsubsection{Reading the results}

Table~\ref{tab:tts} separates the field cleanly into three groups.

\begin{itemize}
  \item \textbf{The VITS exports are unusable here.} RTF $\approx 3.8$ means
        roughly four seconds of compute per second of speech. A 20-second
        answer would take over a minute to synthesise.
  \item \textbf{Piper ``high'' voices are equally unusable}, and for the same
        reason --- RTF $\approx 5.2$--$5.3$, \emph{worse} than the VITS models
        despite Piper's much lighter runtime. The quality tier, not the
        framework, is what blows the budget.
  \item \textbf{Piper low and medium clear the bar with room to spare.} Every
        low voice lands at RTF $\approx 0.61$--$0.64$ and every medium voice at
        $\approx 0.75$--$0.81$. A medium voice synthesises a short sentence in
        about \SI{2}{\second} and a long one in about \SI{8}{\second}, while
        producing more audio than that in playback time --- which is what makes
        sentence-level streaming (\S\ref{sec:latency}) work: playback of
        sentence $N$ outlasts synthesis of sentence $N+1$, so the audio never
        stalls.
\end{itemize}

The gap between low and medium is around \SI{25}{\percent} of compute for a
clearly better voice, which is worth paying given the headroom.

\subsection{End-to-end latency}
\label{sec:latency}

\texttt{python/benchmark.py} measures the stages on the device. Its headline
number is deliberately \emph{not} the sum of them.

Adding up every stage measured in isolation gives an upper bound, not a
latency, because the pipeline does not run them in sequence: vision happens at
photo time, prefill overlaps with recording, and Piper synthesises while
\texttt{llama.cpp} is still decoding. The benchmark therefore reports
\textbf{time to first audio} --- from the moment the visitor stops speaking to
the first word they hear --- counting only the stages still on that path, each
with the figure that applies there: STT in full, the \emph{warm} prefill rather
than the cold one, decode only as far as the first complete sentence, and one
sentence of Piper rather than the whole answer. It excludes the \texttt{aplay}
spawn and Bridge RPC round-trips, so the board is somewhat slower than the
printed figure.

Three mechanisms create that overlap:

\begin{enumerate}
  \item \textbf{Asynchronous prefill.} Once a photo is confirmed, the static
        prefix --- personality instructions plus the element's fact sheet ---
        is prefilled into the KV-cache on a background thread while the visitor
        is still speaking, so only the question needs prefilling at the end.
        The prefix cache is also persisted to disk:
        \texttt{prewarm\_cache.py} computes it once per element
        ($\approx$12 minutes for all 24), so no visitor ever waits through a
        cold prefill.
  \item \textbf{Silence detection with cropping.} Recording stops by itself
        after $\approx$\SI{1.5}{\second} of silence, and the silence is cropped
        from both ends before Whisper sees it. This is not cosmetic: the
        encoder pads every window to a fixed length, so room tone costs exactly
        as much to encode as speech. Thresholds adapt to the noise floor
        measured at the start of each recording.
  \item \textbf{Sentence-level streaming.} Tokens are emitted sentence by
        sentence rather than after the full 60$+$-token generation, so Piper
        synthesises sentence $N$ while the SLM decodes sentence $N+1$. At the
        Piper medium RTF of $\approx 0.8$ measured above, synthesis stays ahead
        of playback and the audio never stalls.
\end{enumerate}

Together these turn the perceived latency from ``sum of four stages'' into
``STT $+$ warm prefill $+$ one sentence of decode $+$ one sentence of Piper''.

\subsection{Third-party components}

Two of these are not optional extras but consequences of the board's form
factor, and are easy to forget when budgeting:

\begin{itemize}
  \item \textbf{USB-C hub.} The UNO Q exposes a single USB-C port on the Linux
        side, and the guide needs three things on it at once --- the camera,
        the headphones and power. A powered USB-C hub with pass-through power
        delivery is therefore required, not a convenience. It must carry
        USB-C PD pass-through (so the board keeps drawing full power while the
        hub is populated), at least one USB-A port for the webcam, and a
        \SI{3.5}{\milli\meter} audio output or a USB audio path for the
        headphones.
  \item \textbf{Power bank.} The guide is carried around a monument, so it runs
        on battery, and it must run at the board's \emph{high-performance}
        profile --- four Cortex-A53 cores saturated by STT, SLM decode and
        Piper, with a USB camera streaming at the same time. The power bank
        therefore needs USB-C Power Delivery at \SI{5}{\volt}/\SI{3}{\ampere}
        ($\ge$\SI{15}{\watt}) sustained, not a \SI{5}{\watt} phone charger
        which will brown the board out mid-answer. Capacity
        $\ge$\SI{10000}{\milli\ampere\hour} covers a full visit with the
        display and radios on.
\end{itemize}
